## Usage estimates: arithmetic passes, scope sensitivities required

I checked every estimate row's stated input formula, cached-input bound, API-cost arithmetic and base totals; all passed. Estimates consolidate stable IDs, distinguish invocations from conversations, retain cache/no-cache sensitivities and keep API dollars separate from the user-reported weekly index. Their request counts, context sizes, source-token approximations and reasoning allowances are uncalibrated assumptions, not statistical bounds or measured usage. The two scenario estimators use different payload/output formulas, so cross-scenario pooling needs a common method first. Endpoint cost differences cannot establish a cost ranking.

Three qualifications materially affect interpretation:

1. **Regression acceptance reserve is not demonstrably matched.** P29 P09 explicitly promises both consequential review and eventual independent patch review. Its estimate nevertheless has the same 4–8-request decision-review basis as p61 A7, while p61 A10 separately budgets 4–8 requests for patch acceptance. The plan has not removed the acceptance gate, and base totals are unaffected. For a path triggering both reviews, add a separately labeled P09 acceptance increment or explicitly justify how its existing range covers both. Using the estimator's identical 4–8-request review allowance gives an illustrative increment of $0.082584–$1.127008 with an already-warm expert conversation, or $0.106904–$1.127008 with one cold start. This is a sensitivity, not observed missing expenditure.

2. **Carrier L6 is misclassified if interpreted from the locked scope.** P43 L6 is queued read-only investigation and hypothetical control design, dependent on S4; it is not an authorized diagnostic-run assignment. The estimate instead places it in future-execution reserve. A mechanical sensitivity moves its $0.004145–$0.058812 from reserve to base, yielding p43 base $0.779677–$8.399820 under unchanged numerical assumptions. Additional actual runs would need a separate scope. Preserve the original estimate alongside this correction.

3. **Carrier future outcomes are not matched.** P17 A7 explicitly owns the full measurement campaign. P43 L5 stops at a reviewed runnable specification, and T3 synthesizes evidence; no equally clear full-matrix execution owner is assigned. The coding acknowledges this, but the usage estimate labels L5 as including matrix execution. Treat execution as an unsupported added estimation assumption or a missing future assignment. Do not present the future reserves as equal-outcome campaign costs. Their completion horizons are also unproven. Within regression, some extra modeled Luna requests arise from splitting core/provider conversations as well as from P06; request growth is not automatically question growth.

Safe reporting: B makes more explicit Luna discovery/support assignments in these samples, retains expert/human gates, and changes some scheduling and neighboring source scope. The size of additional unique useful investigation is coding-sensitive and far below evidence for a tenfold result. All dollar figures remain conditional planning illustrations. Actual quality, runtime, usage, savings and weekly allowance effects remain unmeasured.
