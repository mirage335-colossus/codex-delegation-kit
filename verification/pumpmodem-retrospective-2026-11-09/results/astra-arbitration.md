## Simplest better workflow

1. **Establish the observable work and call path.** Map the real command through complete acquisition, both required tracking lanes, state transitions and endpoint. Preserve one owner for ordered state and global pruning. Parallelize independent preparation/hypotheses within bounded memory; do not invent independent streams or remove required diagnostics to inflate utilization.
2. **Eliminate unnecessary arithmetic before changing hardware.** Count requested transform bins and repeated projections. Compare the existing FFT/ZoomFFT with a singleton reduction or shared projection only where inputs and semantics match. Preserve the existing efficient path elsewhere.
3. **Make acceleration cover a useful computational region.** Batch pure projection/correlation work, retain reusable banks on device, and account for host preparation, transfers, synchronization and setup. Preserve narrow precision exceptions. Tensor peak throughput is not the selection criterion.
4. **Order checks by cost.** Import/configuration, actual constructor and one acquisition, representation roundtrip, extreme geometry/workspace, paired numerical decisions, then representative integrated timing. Only then run the full suite. Freeze measurement-relevant source and artifacts; refresh only the invalidated component while keeping independent acceptance limits.
5. **Delegate distinct questions.** One Luna maps the caller and contracts, one challenges work complexity and device residence, one designs the cheapest falsifier. Screen source applicability before expert arbitration; run supported checks rather than collecting agreement. Keep the selected primary and existing role pins.

I independently consulted [SciPy ZoomFFT documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.ZoomFFT.html), [FFTW's pruned-transform discussion](https://www.fftw.org/pruned.html), and [NVIDIA's matrix-performance guide](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html). They support existing selected-frequency alternatives and shape-sensitive GEMM efficiency, but also warn that fewer arithmetic operations need not improve runtime. These are general mechanisms, not RTX PRO 6000 measurements; current documentation versions do not establish historical library behavior. The study's [primary research](primary-research.md) supplies complementary transfer/timing guidance. No broader literature survey is needed to resolve these bounded judgments.

## Addendum: newer restructuring findings

**Updated judgment:** the newer evidence strengthens the architectural criticism. The earlier work left a substantial, nearly serial recurring bank-preparation cost and continued to expose fine computation as separately dispatched stages. These deserve more weight than the small constructor/wrapper failures. The original five-case packet selection was too narrow to test this whole-receiver prioritization adequately.

I read the original new user request and progress at root physical lines 6855, 6997, 7079 and 7135, inspected frozen `28f08825` and `247b720` source, and read the three new blind reviews. The relevant loop nesting and native caching existed before the new restructuring; the current changes are not themselves evidence of a realized speedup.

**The strongest quantitative missed target is recurring bank preparation.** The captured calibration's actual rows 5 and 7 allocate respectively 0.120946/0.231940 and 0.117075/0.221163 processing seconds per baseband second to recurring banks versus total nominal service: **52.15% and 52.94%**. Four observed bank preparations took 7.02–7.26 seconds with only 0.989–1.004 combined parent/native busy cores despite 12 allocated workers. Native-child CPU time was 5.38–5.53 seconds. These are recurring public-ordinal measurements, not merely startup costs. The [independent cost review and table](new-cost-blind.md) locate these costs without knowing the newer conclusions. Fine work instead accounts for 93–98% in rows 1–3, so the appropriate CPU target depends on the case.

The calibration's Git provenance names `15b17f7d` plus dirty files; the coordinator independently matched all 61 shared-source hashes to frozen `247b720`. The table describes that retained calibration, not the later refreshed final forecast qualification. Its inference that a small `fixed_control` component makes all controller overhead irrelevant is rejected: rendering, projection and waits also occur inside other measured components.

**“Six rebuilds” needs precise wording.** For the reported geometry, 13 epochs × 2 bits × 3 clocks gives 78 lanes, with two channel rays. The coarse builder revisits native synthesis/resampling and projection for each clock/ray combination: six passes per epoch/bit. I verified the loops in both source snapshots. But native `PatternSource` objects are already cached by epoch/bit, with bounded chip caches and shared-bank rendering. There is no retained direct counter proving six object constructions or six complete regenerations of all keyed data. The [bank scout](new-bank-blind.md) correctly preserves this counterevidence. The opportunity is reuse of underlying waveform work across transforms, not simply adding a cache that already exists. Six passes do not imply a sixfold total speedup; transformations remain necessary and reuse must fit memory and fidelity contracts.

**The 2.4% statement uses the wrong denominator if called a whole-cloud-trace share.** I directly read the retained [FP16 disposition](/home/user/___quick/p/_cur/dataPump/pumpModem/local-evidence/current-tensor/fp16/disposition.json). It covers **manual row 3 only**. Fine processing is 1.48248 seconds / 61.76420 seconds of the scaled-FP16 paired driver = 2.4002%; that driver includes 32.32984 seconds of validation-only CPU reference/check work. Fine is 5.2481% of its 28.24786-second common-component sum, which itself includes simulation and is not a separately measured unpaired trace. It is not 2.4% of the full eight-case GPU trace.

Holding those respective denominators fixed, removing fine entirely gives mathematical speedup ceilings of about 1.0246× for that paired driver and 1.0554× for the common sum. These bounds do not transfer to local CPU reception or a changed workflow. The earlier tensor trials targeted coarse transforms: their disposition reports acquisition 4.10346 seconds versus ZoomFFT's 3.54259, with essentially unchanged common sums. Consequently the 2.4% statistic does not make those coarse trials retrospectively irrational; their integrated measurements justify rejecting them.

**A real dependency is being confused with a global barrier.** The [dependency scout](new-dependencies-blind.md) correctly identifies ordered Gaussian updates and segment-level timing/pruning. Its stronger suggestion that all candidates must join every block is not established. Each independent candidate/model chain requires block b before b+1; fixed candidate states within a segment and `_observe_segment` at its end permit investigating a candidate tile carried through rendering, projection, Gram construction and ordered updates. A conservative first version can fuse within a block; processing several blocks per tile is a further bounded option, with more bookkeeping and memory risk. Neither requires concurrent mutation of the native cache or nested executor waits. The existing `bulk_statistics` seam and shared executor should be evaluated before adding another framework.

**Compiler failures also exist.** The same retained disposition records two NVRTC/CuPy CUB setup failures: a rejected local declaration in `POST_MAP`, then an identifier rewritten by output-name substitution. I also verified the original child stderr at physical lines 1040 and 1090, retained in [compiler excerpts](gpu-compilation-excerpts.json). Both reached zero numerical assertions and were repaired before the successful experiment. This extends the earlier evidence beyond Python failures: no native CPU compilation failure was established, but GPU runtime compilation did fail. These are localized toolchain integration misses, not proof that the tensor architecture was unsound.

The next architecture discriminator should combine the new lenses. On a small existing native-bank fixture, count source construction, chip-tile creation, render requests and coordinate work separately; compare existing scheduling with bounded reuse across clocks/rays, checking projected columns, Gram/rank, candidates and peak memory. Then compare unfused versus fused candidate tiles on two segments, including erasures, posterior state, quiet statistics and exact global pruning points. Predicted evidence is fewer repeated native calculations and dispatch barriers with identical required results; failure of equivalence or memory bounds rejects that variant. These are recommendations for an authorized implementation owner, not new production work under this retrospective.

The three fresh Luna reviews independently expose cost concentration, serial provider access and stage/dependency limits. They do not independently prove the six-pass saving, and they require the corrections above. Their targeting was informed by the new user concern; preserve them as a separate exercise, not an improved score for the original 18 responses. Existing primary research on batching, transfer cost and actual-shape benchmarking remains applicable; the strengthened conclusions come from original receipts, source dependencies and arithmetic, so another broad literature search would add little. The better approach is whole-work cost and dependency review before hardware specialization, with executable discriminators and a strong owner resolving conflicting interpretations.
