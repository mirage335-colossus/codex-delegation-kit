# C2 general review

**Decision:** The short CPU/CUDA fine comparison is useful as a parity and work-accounting smoke check, but it is insufficient to estimate complete receiver throughput or credible margins. Before a full cloud campaign, run one bounded, representative end-to-end experiment on a single native capture: CPU acquisition through fine processing, failed candidates/retries, recurring setup, and quiet-slot completion. Measure phase and total wall time with the intended 12-thread allocation; compare CPU and any proposed GPU-assisted path on matched work. Keep the comparison explicitly scoped to the actual host and stream topology.

## Concerns

1. **End-to-end scope is absent (known limitation, not a code defect).** _case_probe performs acquisition on CPU once, then samples only three fine strata for each device; the report states that short endpoints may be incomplete and sets both local_cpu_service_established and complete_receiver_qualification false (gpu_workload.py:172–201, 241–247). Those measurements omit the receiver work the user wants estimated, including failed-candidate acquisition and completion/setup costs. **Predicted outcome:** fine parity may pass while total throughput or the CPU bottleneck differs materially. **Cheapest decisive check:** time one representative native capture end-to-end on the 12-thread CPU configuration, recording phase totals and completion. **Action:** retain this probe as a fine-stage gate; require the end-to-end measurement before choosing a full campaign or claiming complete throughput.

2. **The test does not establish productive 12-thread same-stream behavior (unverified hypothesis).** Worker count is configurable and CPU allocation is resolved for one job with one numerical thread; the CUDA policy says controller and dedicated workers share the selected default stream (gpu_workload.py:218–224, 242–246). The excerpt does not show whether this topology overlaps useful CPU work or queues GPU work serially in the intended receiver. **Predicted outcome:** an event/timeline trace may show idle CPU workers, GPU queueing, or little benefit from the configured workers; this is not inferable from parity. **Cheapest decisive check:** trace one representative end-to-end run at the intended 12 workers, including CPU utilization and synchronized GPU intervals. **Action:** preserve the shared-stream configuration only if it supports the required throughput; otherwise test the smallest alternative stream/worker topology before campaign expansion.

3. **One ordered pair cannot establish repeatability or margins (known limitation).** The policy caps cases at three, uses one pair per case, and runs CPU before CUDA; the final status records short-work parity, not throughput qualification (gpu_workload.py:222, 242–247, 264–278). **Predicted outcome:** warm-up/order effects or run-to-run timing variation remain invisible, so a fast-looking result cannot support credible margins. **Cheapest decisive check:** repeat matched measurements on the same capture with alternating device order and report spread alongside synchronized timings. **Action:** use that small repeat to decide whether timings are stable enough to justify a larger campaign; do not interpret the parity status as a speed or margin result.

## Choice to preserve

The probe fixes acquisition coordinates from one CPU result and compares CPU/CUDA fine work on the same prepared capture, while hashing inputs/sources and explicitly withholding complete-receiver qualification (gpu_workload.py:177–201, 230–247, 264–278). That is a clean, bounded way to test fine-stage parity without overstating what it proves. Preserve the FP64 policy and accuracy checks in this gate.
