# C1 architecture review

## Objective and first decision

The target is complete one-stream receiver throughput on the local 12-logical-thread CPU, including acquisition, fine tracking, failed candidates, recurring setup, and quiet-slot completion. Independent simulations do not answer this objective. With no profile percentages, do not select a kernel or parallelization target from these excerpts alone. First capture a matched end-to-end baseline and attribute wall time and process CPU time to setup/acquisition, block preparation/projection, state updates, and completion. For the block path, record block sizes, candidate/tap counts, job counts, executor queue/active-worker time, and wait time. This can separate repeated work (high CPU in preparation), controller serialization (wall wait with idle workers), and worker shortage (ready work with saturated workers). Report throughput and latency as well as CPU use.

## Concerns to resolve (hypotheses unless stated otherwise)

1. **The streaming axis is state-dependent; the available parallel boundary is within a block.** The score-block path computes shared correlations/Gram data and then updates each runtime for that block (triad_incremental_receiver.py:281–303). A later block's elapsed time and update state depend on the prior block (lines 290–300, 327), so batching blocks or parallelizing time is not justified by these excerpts. The executor path submits all current-block jobs before collecting results (lines 308–325), so the ordered result() loop alone does not prove tasks execute serially. **Predicted observation:** attempts to parallelize blocks add synchronization/state hazards; runtime jobs may overlap if there is enough independent work. **Cheapest decisive check:** instrument per-block runtime job count, submit/queue/run/wait wall times, and active workers on the matched stream. **Action:** preserve the block recurrence; tune only the measured within-block job partition or task granularity. Do not assume all recurrences have independent jobs.

2. **The two tracking lanes are explicitly stepped one after another.** push invokes nominal then adaptive, passing the same input (triad_tracking_receiver.py:714–717); their results are mixed only after both updates (lines 726–735). This is a concrete serialization point and a plausible one-stream CPU parallel boundary, but the excerpt does not establish absence of shared mutable callback/workspace state. **Predicted observation:** if lane work is substantial and independent, concurrent lane execution may reduce push wall time while aggregate process CPU rises; if overhead/contention dominates, it may not. **Cheapest decisive check:** time each lane separately on identical representative inputs and inspect whether they share mutable state before a small matched concurrent prototype; verify coverage, scores, and failure propagation. **Action:** parallelize lanes only if that check confirms independence and end-to-end wall-time gain; otherwise retain ordering.

3. **Projection setup may be repeated for every nonstandard block.** In DFT mode, when rows != self.projection.samples, score-block calls BlockProjection.make (triad_incremental_receiver.py:247–248); make constructs frequency and mask arrays over the full block (triad_dynamic_joint.py:72–86). This is O(N) setup/allocation per such call, before the transforms and contractions. Whether those calls recur often enough to matter is unknown. **Predicted observation:** repeated same-size blocks rebuild identical projection indices and spend measurable CPU in construction. **Cheapest decisive check:** count (rows, projection.samples) cases and time/call-count make on the matched stream. **Action:** if recurring, cache projections by the complete relevant key (size, rate, required/excluded bands); otherwise leave it alone.

## Choice worth preserving

The block shares one projection and observation across alternatives, computes correlations and Gram information once, then gives independent state updates the same block quantities (triad_incremental_receiver.py:274–289, 305–310). Preserve this shared-work boundary while measuring and tuning; duplicating block preparation per lane/runtime would risk multiplying expensive work.
