# Expanded integration follow-up

This is additional evidence from the same supplied `28f08825` snapshot at `/tmp/pump-review-baseline28`; it does not replace or edit the original report. I did not inspect subsequent evidence/results or other repositories.

## Findings

1. **The actual workload is a fine-stage CUDA probe, not a complete CUDA receiver forecast.** `triad_gpu_workload.run_probe()` admits CUDA only when CUDA is available ([triad_gpu_workload.py](/tmp/pump-review-baseline28/tools/triad_gpu_workload.py:209)), allocates one numerical thread per requested worker ([line 218]), and calls `configure_numerical_threads()` ([line 221]). `_case_probe()` first performs acquisition with a CPU `CompleteBitReceiver`, then records short fine checkpoints for CPU and, when requested, CUDA ([line 177], [line 194]). Its own report says `complete_receiver_qualification=False` and limits scope to short fine checkpoints ([line 241], [line 245]). For a 12-worker run, the allocation uses 12 workers × 1 numerical thread; that is distinct from twelve threads inside each worker.

2. **The proposed coarse screen subclass fails at the canonical constructor guard.** The workload gets its screen through `PreparedCapacityCase` → `PreparedReplay` → `build_public_screen` ([triad_case_capacity.py](/tmp/pump-review-baseline28/tools/triad_case_capacity.py:104), [triad_case_replay.py](/tmp/pump-review-baseline28/tools/triad_case_replay.py:455), [line 495]). `build_public_screen` has a `screen_factory` parameter ([triad_case_replay.py](/tmp/pump-review-baseline28/tools/triad_case_replay.py:346), [line 400]), and `PreparedReplay` accepts it ([line 458]); however `PreparedCapacityCase` calls `PreparedReplay` without forwarding a factory ([triad_case_capacity.py](/tmp/pump-review-baseline28/tools/triad_case_capacity.py:104)). More decisively, `CompleteBitReceiver.__init__` rejects subclasses with `type(screen) is not FFTScreen` ([triad_receiver.py](/tmp/pump-review-baseline28/tools/triad_receiver.py:506)). Its coarse path copies/partitions the canonical screen and invokes its projection, plan, and score interfaces ([triad_receiver.py](/tmp/pump-review-baseline28/tools/triad_receiver.py:600), [line 638]); a GPU implementation must preserve those contracts and the complete two-bit proposal set.

3. **Fine CUDA routing already exists through the production receiver path; a device subclass is not the current seam.** `_case_probe` constructs `CompleteBitReceiver(..., fine_device=device)` ([triad_gpu_workload.py](/tmp/pump-review-baseline28/tools/triad_gpu_workload.py:174)). `FineReceiverContext` validates CUDA plus FP64 and prepares CUDA linear algebra ([triad_receiver.py](/tmp/pump-review-baseline28/tools/triad_receiver.py:371), [line 377]); it fingerprints the selected device at [line 409]. `FineSession` directly constructs `PracticalTrackingReceiver` with that device ([triad_receiver.py](/tmp/pump-review-baseline28/tools/triad_receiver.py:228), [line 236]). If an alternate fine callback subclass is specifically required, this direct construction has no callback factory; otherwise the supported `fine_device` route is already the integration contract. Fine results preserve CPU-facing likelihood/state outputs under the existing canonical receiver path.

## Minimal check and limits

I ran a one-thread constructor preflight using a minimal `DeviceFFTScreen(FFTScreen)` instance created with `object.__new__`. The first inline command had a Python quoting/syntax error before imports or assertions (zero assertions). The corrected scratch wrapper `/tmp/pump-review-expanded-integration/subclass_preflight.py` completed in 2.0 s and caught the expected `TypeError: complete bit backend currently requires the canonical whole FFTScreen` (one constructor-guard assertion). This directly verifies the subclass blocker; it does not test GPU execution, coarse score parity, or end-to-end forecast timing. A minimal integration change would need to plumb the screen factory through `PreparedCapacityCase` and relax/replace the exact-class guard with an explicit validated interface, then compare the same canonical coarse proposals and complete work receipts before attempting forecast timing.
