# C1 executable-falsifier review

## Concerns

1. **Do not assume model-update threading is the first win.** `_score_block` does DFT projection of the observation and of the entire `[3,candidates,taps,rows]` basis (lines 243–250, 274–289), then constructs Gram/correlation tensors before runtime updates. This could dominate the executor stage, but the packet gives no phase profile. **Prediction:** if projection/basis preparation dominates, increasing executor workers barely changes complete single-stream wall time. **Cheapest check:** replay one fixed, representative single-stream observation after warmup with executor disabled and with 2/4/8/12 workers; record wall time plus separate projection/basis and update wall times, holding thread-pool settings and all work fixed. Compare final scores and work counts. If preparation dominates and outputs match, optimize that measured stage before adding workers; otherwise retain model updates as a candidate.

2. **The practical tracking controller serializes two full lanes.** `push` calls nominal then adaptive synchronously (tracking receiver lines 713–717); both receive identical inputs and `_combine` later mixes scores and verifies coverage (726–745). This is an evident serialization point, but whether lane-level concurrency helps depends on each lane's internal threading and the controller's complete-observation workload. **Prediction:** overlapping the lane pushes helps only if their wall intervals overlap useful CPU work without increasing total work or degrading throughput through oversubscription. **Cheapest check:** on one fixed observation, compare sequential and experimental concurrent lane execution at the same total worker budget; time the pair and check processed rows, consumed samples, completion flags, work counts, and score tolerance. If no wall-time gain, keep the simpler sequential controller; if gain with equal coverage/results, consider bounded lane parallelism.

3. **The present executor path has no demonstrated scaling or overhead break-even.** `_score_block` submits independent runtime jobs then waits on all futures (incremental receiver lines 301–326); it permits overlap, but small jobs or internally threaded Torch/NumPy may make a thread pool slower or oversubscribed. **Prediction:** worker scaling will flatten or regress when task granularity is too small or nested threading consumes the CPU budget. **Cheapest check:** use the same warmed single-stream replay and inputs for 1/2/4/8/12 workers, report end-to-end wall time and process CPU, and verify identical coverage and numerical tolerance. Retain threading only at worker counts with repeatable single-stream benefit; cap inner library threads if the controlled comparison shows oversubscription.

## Choice worth preserving

Keep the separation between shared immutable block observations and independent model state updates, and drain submitted futures even after a task fails (lines 305–326). That structure offers a clean concurrency seam while preserving failure visibility. The packet does not establish that any cited stage is currently a defect or bottleneck; these are falsifiable prioritization hypotheses.
