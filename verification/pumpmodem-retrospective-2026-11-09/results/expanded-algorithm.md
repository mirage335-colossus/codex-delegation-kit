# Expanded algorithmic follow-up

## Assignment and scope

- Source supplied by the coordinator: frozen `pumpModem` baseline `28f08825`, extracted at `/tmp/pump-review-baseline28`. The extraction has no `.git` metadata, so I could not independently resolve that short revision to an object.
- Read-only inspection was limited to `tools/`, `tests/`, and `_tests-RobustModem.md` in that extraction. I did not inspect product documentation, history, current checkout source, or other research responses. The manual notes describe receiver regimes including sub-9 kHz, 500 kHz, HF 30 MHz/36 Hz, and EME 5.8 GHz/360 Hz cases; the Python receiver tests are synthetic and should not be treated as representative performance data.
- Question: identify algorithmic work plausibly removable before scaling complete reception across 12 logical CPUs and a fast GPU. Findings below are source predictions, not measured receiver speedups.

## Findings

1. **Avoid recomputing the observation projection for both fine-tracking lanes.** `PracticalTrackingReceiver.push` sends each identical chunk first to `nominal` and then `adaptive` (`tools/triad_tracking_receiver.py:709-717`). Both lanes are constructed from the same receiver arguments and share the same `samples`, block size, DFT projection policy, masks, and segment calendar. Each lane's `IncrementalGaussianReceiver._score_block` independently calls `projection.numpy(values)` for an observed DFT block and independently computes its projected energy (`tools/triad_incremental_receiver.py:239-267`). The basis differs between lanes, but the input projection does not. A shared per-block projected observation plus energy/null-statistic result can remove one forward DFT and duplicate energy calculation per block, without changing either lane's likelihood; retain per-lane projections if later contracts permit lane-specific masks, block calendars, or bands. Smallest check: a two-lane one-block wrapper compares current per-lane projected vectors, energy and scores against one shared projection for valid and fully erased blocks, then a multi-block check covers the merged terminal block. This is likely the cleanest CPU-side elimination even when likelihood updates run on GPU.

2. **Remove the analytically known H0 Gaussian update from candidate/model kernels.** `_TimingStream` requires the rendered H0 basis to be exactly zero and checks the resulting H0 evidence is exactly zero (`tools/triad_tracking_receiver.py:226-232, 257-259`). `IncrementalGaussianReceiver._score_block` nevertheless forms three-hypothesis Gram/correlation tensors (`tools/triad_incremental_receiver.py:270-289`) and submits them to every Gaussian model update (`:301-326`). Those updates perform covariance eigendecomposition and Cholesky (`tools/triad_gaussian_state.py:213-238`); zero H0 still follows those general kernels. At segment transport, the H0 posterior is already constructed analytically as zero mean and stationary power covariance (`tools/triad_tracking_receiver.py:516-519`), and the code asserts its evidence stays zero. I ran one bounded actual-helper check against `GaussianStateFilter`: three zero-observation blocks with 4 candidate rows and 2 taps, finite `.5 s` coherence, retained score zero and stationary-prior posterior each time; result passed in `0.247079` process CPU seconds. Removing H0 from tensor/update work while supplying its exact zero evidence and analytic posterior should save one of the three hypothesis slices of repeated Gaussian work (not one-third of total receiver time). Smallest acceptance check: compare full two-bit score and transferred H0/bit posterior against the existing path over finite/infinite coherence, multiple taps, and both precisions; verify exact zero H0 remains asserted. The current API labels three hypotheses and tests may encode that shape, so this is a scoped kernel/API change rather than a drop-in edit.

3. **Offer an operational-only fine mode that skips the adaptive lane when its diagnostics are not requested.** Endpoint classification reads `tracked['lanes']['initial_affine']` for bit evidence and quiet-energy evidence (`tools/triad_receiver.py:447-463`); the adaptive combined evidence is explicitly marked diagnostic-only (`:464-468`). The complete path still constructs both lanes (`tools/triad_receiver.py:228-240`), pushes every chunk through each sequentially (`tools/triad_tracking_receiver.py:709-717`), and computes the half/half mixture (`:726-750`). A caller that only needs the present DATA/QUIET/AMBIGUOUS decision can avoid adaptive scoring and its posterior/transition work. This does change the returned diagnostic payload and removes the documented fixed half/half reported mixture, so it should be an explicit product mode and preserve the existing full mode wherever that mixture or adaptive diagnostics are part of the contract. Smallest check: run the same deterministic complete windows with the optional lane disabled and verify initial-affine scores, operational decision, quiet statistic, coverage, and public work receipt match the full path; separately assert the diagnostic-only fields are absent/labelled.

## Relevant constraints and counterevidence

- The two fine lanes are intentionally not interchangeable: one preserves the original affine waveform and drives the operational decision; the adaptive lane provides a fixed-prior mixture with an evidence bound. Do not silently select the stronger lane or discard the mixture while claiming unchanged receiver semantics (`tools/triad_tracking_receiver.py:631-644, 726-750`; `tools/triad_receiver.py:447-472`).
- `tracking_source_basis` already shares one bounded mapped-template cache with its `initial_affine` renderer (`tools/triad_continuous.py:316-383`). Therefore the repeated work in item 1 is strongest for observation DFT/energy and per-lane interpolation/projection plumbing; it is not evidence that native source templates are fully regenerated twice.
- The coarse FFT screen already shares projected input across workspace partitions in the complete receiver path, and its lag method retains only bounded candidate rows per workspace (`tools/triad_receiver.py:638-691`; `tools/triad_realtime_fft.py:912-975`). I found no source-only basis to cut its full public frequency/arrival search without changing search coverage or calibrating a new proposal rule. Existing tiling and candidate caps are already explicit.
- Twelve workers do not imply all fine work scales twelvefold: source rendering, NumPy projection/Gram construction, and global timing prediction/merge remain owner-side around separately scheduled likelihood jobs (`tools/triad_incremental_receiver.py:274-289, 301-326`; `tools/triad_tracking_receiver.py:466-522`). GPU assist can accelerate likelihood kernels, but these CPU stages remain in the critical path; no source evidence establishes a speedup for either hardware configuration.
