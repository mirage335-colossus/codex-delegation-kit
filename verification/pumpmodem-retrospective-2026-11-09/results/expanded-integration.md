## Findings

1. **Cheapest preflight blocks any GPU exercise in this environment.** Using the assigned interpreter and one-thread limits, `OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 /tmp/pumpmodem-cleanup-venv/bin/python -c 'import torch; print({"torch":torch.__version__,"cuda_build":torch.version.cuda,"cuda_available":torch.cuda.is_available(),"torch_threads":torch.get_num_threads(),"device_count":torch.cuda.device_count() if torch.cuda.is_available() else 0})'` returned `torch=2.8.0+cpu`, `cuda_build=None`, `cuda_available=False`, `torch_threads=1`, `device_count=0` (1.2 s wall). This invalidates GPU parity/performance execution on this runner, not the architecture. A CUDA-equipped interpreter/device is required for that evidence.

2. **The fine stage already has a CUDA-capable numerical path, but the complete receiver never selects it.** `DynamicJointReceiver` accepts `device` and checks CUDA availability plus FP32 TF32/matmul settings at [triad_dynamic_joint.py](/tmp/pump-review-baseline28/tools/triad_dynamic_joint.py:119); its `correlations()` moves each raw block to that device and performs FFT/projection there ([lines 245–293]), while `score_correlations()` returns NumPy CPU arrays after synchronization ([lines 295–318]). `ScanJointReceiver.score_correlations()` likewise consumes canonical correlation blocks, uses its prepared state, and returns CPU arrays ([triad_dynamic_variants.py](/tmp/pump-review-baseline28/tools/triad_dynamic_variants.py:99)). But `WeakReceiver.score()` hardcodes `device='cpu'` at [triad_weak_receiver.py](/tmp/pump-review-baseline28/tools/triad_weak_receiver.py:143), and its constructor directly chooses imported `FFTScreen`/`SegmentedFFTScreen` classes ([lines 76–79]); there is no screen/receiver factory or device option. So a fine-stage subclass alone is not reachable through this canonical full-receiver path. The minimum wiring seam is constructor-level injection or a device option/class selection in `WeakReceiver`, while preserving its fixed-grid snapping, both-bit check, CPU result shape, null check, and operational decision ([lines 129–161]).

3. **The coarse screen is a separate CPU numerical implementation; subclassing does not inherit GPU execution.** `FFTScreen` builds NumPy columns/Gram/FFTs and its scoring path calls SciPy FFT helpers ([triad_realtime_fft.py](/tmp/pump-review-baseline28/tools/triad_realtime_fft.py:490), [568–590], [869–889]). `SegmentedFFTScreen` overrides `_score_grid()` with SciPy FFTs over NumPy scores ([triad_segmented_fft.py](/tmp/pump-review-baseline28/tools/triad_segmented_fft.py:205–235)). A device subclass must explicitly move/implement these hot kernels (or a narrower set of FFT/correlation helpers), then return the same per-workspace score arrays to inherited CPU peak/NMS selection. Existing tests define a cheap acceptance boundary: both bits retained; candidate keys/order stable and scores close across precision; direct arithmetic equality for segmented score grid (`test_triad_realtime_fft.py:664–672`, `test_triad_segmented_fft.py:55–60,74–95`). Candidate selection is a proposal only, not final admission (`triad_realtime_fft.py:869–871`).

4. **“All 12 CPU threads” needs explicit controller configuration, not just setting `fft_workers`.** `WeakReceiver` defaults SciPy FFT workers from `resolve_cpu_budget()['threads']` and fingerprints that count plus the current `torch.get_num_threads()` ([triad_weak_receiver.py](/tmp/pump-review-baseline28/tools/triad_weak_receiver.py:42–47,88–95)); it does not set PyTorch/BLAS thread counts itself. `triad_cpu.configure_numerical_threads()` is the available setup helper (`triad_cpu.py:236–275`), which must run before receiver/workers for explicit threadpool/Torch setup (`triad_cpu.py:287–295`). The weak-receiver tests check worker propagation and fingerprinting, not thread configuration (`test_triad_weak_receiver.py:12–35`). For a twelve-thread forecast, configure/record the allocation first and keep the GPU execution’s own synchronization/timing separate from CPU preparation and transfer time.

## Coverage limits and next check

Source predicts the CPU-only routing and the existing callback/output contracts; no GPU runtime behavior was observed. The CUDA check above is the minimal environment preflight and fails before numerical assertions (zero GPU assertions). Next useful check, once a CUDA-enabled runtime is available, is a tiny matched fixture through the same canonical receiver with CPU and CUDA coarse/refinement implementations: compare candidate identities/bit coverage and bounded score error, verify `hypothesis_log_evidence[..., 0]` remains the required zero null, and record end-to-end CPU/wall stage timings under an explicitly configured 12-thread allocation. Do not claim complete receiver GPU acceleration from the already-supported fine `device` path alone.
