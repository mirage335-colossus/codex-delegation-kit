## Concerns

1. **FP32 projection may lose small residuals even when the in-band spectrum has modest dynamic range.** At `triad_incremental_receiver.py:274-280`, the callback basis is accepted as complex128 and passed through `projection.numpy`; the code checks finiteness, but this excerpt provides no condition or accuracy check for the projection. If the projection subtracts nearly aligned components, computing it in FP32 can discard the residual that becomes the informative template. The spectrum's dynamic range alone does not establish that this operation is well-conditioned. **Predicted outcome:** projected template norms/correlations and candidate scores differ, potentially changing a close candidate decision. **Cheapest decisive check:** on a small fixed set of matched real blocks, compare projected basis and resulting scores from FP32 projection with the existing complex128 path, including the closest competing scores. Include acquisition, tracking, and unsuccessful-candidate examples; extend to setup/quiet-slot blocks if their inputs differ. Set acceptance from the receiver's required score/decision margin, which this packet does not specify. If projection error consumes that margin, keep projection (or just its sensitive substep) in FP64 and retain bulk FP32 elsewhere.

2. **FP32 Gram error may conflict with a stricter downstream PSD contract.** The excerpted incremental path currently forms `gram_np` in NumPy at `triad_incremental_receiver.py:281-282`, while `r` is calculated from tensors at lines 285-289; the candidate would move Gram computation to FP32 too. The Gaussian state accepts complex64 with default relative tolerance `2e-5` and rejects more-negative Gram eigenvalues at `triad_gaussian_state.py:71-74, 96-110`. Separately, `triad_gaussian_prepared.py:52-62` converts Gram to complex128 and checks PSD against `1e-10`. If candidate FP32 Grams feed that prepared path, converting them to double will not recover PSD lost to FP32 roundoff, and inputs acceptable to the streaming state may fail preparation. Whether the prepared path consumes these same Grams is not established by the packet. **Predicted outcome:** state/prepared disagreement or a rejection for a roundoff-sized negative eigenvalue. **Cheapest decisive check:** run the same small matched Gram set through both downstream consumers; record each minimum eigenvalue divided by Gram scale, the configured checks/repairs, and acceptance. If the prepared path is in scope, either retain higher-precision Gram formation for its inputs or explicitly align its validation/repair policy with a demonstrated application error bound; do not assume a double cast fixes the issue.

## Choice to preserve

Keep the Gaussian state and cumulative likelihood work in CPU FP64 as proposed. The excerpts show covariance/eigenvalue validation and likelihood accumulation downstream, while the large mapped-basis and correlation work is the proposed GPU target. This is a simple boundary that avoids expanding lower-precision state error across blocks; qualify the FP32 inputs at the actual consumer boundary before moving more arithmetic.

## Minimal preflight

Use a deterministic, compact set of matched blocks from the listed receiver work types. Compare current complex128 projection/Gram and candidate FP32 outputs, then feed both through the same CPU-FP64 Gaussian consumer(s). Report relative projection/correlation differences, scaled Gram minimum eigenvalues, final score differences, and whether any close candidate ordering or downstream acceptance changes. This preflight can reject an unsafe boundary cheaply; it cannot establish throughput or complete-work coverage, which remain separate acceptance conditions.
