# C5 falsifier review

## Concrete concerns

1. **FP32 feature errors can survive the FP64 state.** The proposal computes correlations and Grams in FP32, while the state keeps only its accumulated likelihood in FP64. In the excerpt, `r` and `gram` are both formed/cast at lines 281–289, and the state documentation says the likelihood is FP64 (Gaussian state lines 65–73). A small perturbation to `r` or `gram` can affect posterior updates before the scalar likelihood is accumulated; FP64 accumulation cannot restore that information. This is a hypothesis, not a demonstrated defect. **Cheapest decisive check:** for a small deterministic block, run the same projected `y` and `B` through a complex128 reference and complex64 feature path, then feed each pair to the Gaussian state in FP64; include a nearly dependent tap pair and observations with a weak component along its small-eigenvalue direction. Compare final likelihood ratio, posterior mean/covariance, and any downstream accept/rank decision against the application’s stated accuracy margin. If discrepancies exceed the margin, retain FP64 for the sensitive feature stage or use selective FP64 fallback; otherwise keep the proposed boundary for this tested envelope.

2. **Device Gram construction may cross the state’s PSD/Hermitian checks.** The current excerpt constructs `gram_np` with NumPy `einsum` and later casts it, while the proposal moves Gram arithmetic to FP32 device (receiver lines 281–289). The state checks Hermitian symmetry and negative eigenvalues against `relative_tolerance` (lines 96–110; default complex64 tolerance is 2e-5 at line 73). Reduction-order roundoff can produce asymmetry or a negative eigenvalue that trips validation, or gets repaired and changes the likelihood. **Cheapest decisive check:** use the same small `B` as the first check, build `BᴴB/variance` via the proposed device reduction, and record asymmetry, minimum eigenvalue relative to scale, repair diagnostic, and whether the state accepts it; compare to complex128. If the check fails or repair exceeds the accuracy budget on ordinary blocks, symmetrize/recompute Gram in higher precision or add a documented fallback. This too is unverified, not an observed defect.

## Choice worth preserving

Keep Gaussian state updates and likelihood accumulation in FP64 on CPU. It provides a clear precision anchor for iterative/cumulative calculations while the bulk mapped-template, projection, correlation, and Gram work is evaluated separately for FP32 suitability.
