## Findings

1. **The 12-worker bank budget does not expose all bank work to 12 workers.** `PreparedCapacityCase` passes `bank_workers` into `PreparedReplay`; the suite test checks that 12 is passed. `build_public_screen` passes it to `FFTScreen`, but mapped native basis acquisition is through one `NativeStream` pipe: `FFTScreen.__init__` calls the provider synchronously, and `_bounded_basis` issues sequential `basis_mapped` requests. In C++, non-shared mapped requests loop candidate rows and call `shaped_basis_mapped` serially; `PatternSource` is explicitly private-cache / one-worker-at-a-time. Python parallelism is currently the mapped FIR projection pool, while `_bank_arrays` FFTs one lane at a time over only the 1–2 ray rows. Thus 12 is a requested allocation, not evidence of 12 busy cores during native synthesis or the per-lane FFT loop. This is a source prediction; no matched utilization run established the bottleneck. **Cheapest proof:** instrument calls/time for native basis, projection, Gram, and FFT phases on a small fixed public bank; compare 1/6/12 workers with identical address, geometry, memory cap and source, recording elapsed plus process/native CPU. First batch the existing `bank_columns` lane dimension into one FFT along its last axis and compare transformed columns, ranks/projectors, and proposal scores against current results; this naturally gives the FFT library more independent transforms. For native scaling, prototype parallel row work only across distinct `PatternSource` objects (one worker per instance) and preserve the 64 MiB exporter/request bound.

2. **The per-lane Gram calculation makes redundant full-column copies.** `FFTScreen._bank_arrays` at `tools/triad_realtime_fft.py:599-603` evaluates `columns.astype(np.complex128)` twice for each lane, once before conjugation and once for the right operand. The canonical public builder requests `precision='fp64'` (`tools/triad_case_replay.py:401-412`), so both casts are already complex128 inputs; default `astype` still copies. Over every epoch/bit/clock bank this adds repeated full-kernel memory traffic and temporary allocation without changing the Gram result. A local `wide = np.asarray(columns, dtype=np.complex128)` followed by `wide.conj() @ wide.T` preserves fp64 accumulation and avoids the redundant cast copy (the conjugate temporary remains). **Cheapest proof:** compare old/new Gram matrices, eigensystem/ranks, and scores on the existing small `FFTScreen` fixture; then time just bank construction on the same fixed bank and inspect peak RSS/allocations.

3. **Mapped bank staging clears nearly every element before overwriting it and allocates a chunk-sized product temporary.** In `tools/triad_realtime_fft.py:496-507`, each lane batch allocates `np.zeros((lanes, coarse_rows), complex128)`, then fills the whole mapped grid in chunks except at most the one final padded raw index. The formula at lines 454 and 499 means `keep` is true for every index below `raw_kernel_rows`; the only possible false entry is the terminal ceil-padding point, which needs zero extension. The assignment `supplied * np.exp(...)` also materializes a full product array before copying into `coarse`. `np.empty`, explicit zeroing of the invalid terminal column only, and `np.multiply(supplied, phase, out=coarse[:, first:stop])` can avoid most clearing and product-copy traffic while retaining the same zero extension. **Cheapest proof:** deterministic fake-provider comparison of the coarse arrays and final projected columns for both divisible and non-divisible `raw_kernel_rows / sampling_step`, including a delayed ray; require exact equality before timing and peak-memory comparison.

4. **GPU assistance accelerates projection/scoring but does not parallelize or move keyed basis generation.** The GPU backend wraps the canonical screen, but `GpuFFTScreen._projection_pool` is a `nullcontext`, `_project_mapped_bank` consumes the host `coarse` array on device, and the native exporter still provides keyed samples over the serial pipe. The existing CPU forecast explicitly matches coarse work and recurring-bank work, then retains a local CPU holdout (`triad_gpu_cpu_forecast.py:26, 291-321, 356-367`; `triad_gpu_bank.py:130-158`). It is therefore usable for forecasting the projected/FFT portion only when its receipts match; a fast GPU bank result alone does not establish fast end-to-end bank construction. **Cheapest proof:** use the existing paired CPU/GPU bank comparison and report native basis-call CPU/wall separately from GPU projection/FFT time; verify the sum against end-to-end bank preparation on the held-out public ordinal.

## Nearby tests and limits

`tests/test_triad_case_replay.py` covers bounded native-coordinate splitting and the public bank builder through mock sources; it does not exercise C++ thread scaling. `tests/test_triad_case_suite.py:84-139` asserts full-logical worker selection and configuration-hash reuse for duplicate rows, but not productive utilization. `tests/test_triad_case_capacity.py` checks capacity/model guardrails, not coarse-bank scaling. Existing cache reuse is already substantial: the native exporter retains keyed `PatternSource` instances by `(epoch_offset, bit)` across basis calls and can share pulse/NCO work for identical geometry (`triad-helper-export.cpp:1327-1329, 1555-1641`; `triad_modem_v3.hpp:91-106`). Address changes intentionally clear that cache. I found no evidence here that repeated source identities within one bank are recomputed from scratch, nor evidence to justify reusing a bank across different public epochs/ordinals.
