## Scope and rationale

Added one optional native role, `astra_expert`, pinned to `gpt-6-astra` at medium
effort, without a service-tier override. All eight existing role files and
controller/runtime modules remain unchanged. The new role is a read-only adviser
on one consequential question, not another scheduler, mandatory reviewer or
automatic repair stage. It can inspect relevant historical diffs, original user
wording, conflicting evidence and simpler architecture alternatives. The normal
engineering owner keeps integration and acceptance responsibility.

The mixed-model policy permits a narrowly gated Sol-to-Astra consultation while
preserving hard Luna-only/inherit-only limits. An hourly strategy checkpoint is
considered during existing progress updates, not an unconditional model call or
automation. No timer, new state store or per-task controller model override was
added. The role requires an explicit finite assignment budget; its time, context
and output limits are instructions rather than enforced billing limits. Current
account access and observed effective settings must still be checked at use.

Selection favors unresolved causal contradictions, difficult cross-component or
mathematical reasoning, consequential prompt/acceptance ambiguities and costly
architecture choices. Missing cheap differential tests should be restored first;
they do not themselves establish model insufficiency. The adviser must return
checkable predictions and minimal alternatives, including retaining the current
approach. Routine editing, elapsed time, agent agreement and repository size are
insufficient triggers. Existing history carries the consultation decision and
findings; no duplicate bookkeeping is required.

## Research used

Sources were read on October 21, 2026. These support task-fit hypotheses, not
proof of account access, measured savings or guaranteed superiority.

- [OpenAI model-selection guidance](https://developers.openai.com/api/docs/guides/model-selection)
  positions Astra for ambiguity and deep analysis, while identifying GPT-6.1 Sol
  for complex work with time/cost constraints. It recommends matched-task
  experimentation and retaining the lightest adequate setting. This informs
  selective consultation rather than a default escalation ladder.
- [Official Astra model reference](https://developers.openai.com/api/docs/models/gpt-6-astra)
  confirms the identifier and medium reasoning option. No parameter count was
  verified; neither an assumed parameter count nor raw context capacity is a
  selection rule. API specifications and prices do not establish Codex account
  availability, effective runtime settings or subscription usage charges.
- [Direct community reports on Astra's value](https://www.reddit.com/r/codex/comments/1w8t735/how_are_you_using_gpt6_astra_in_codex_and_is_the/)
  include both users reporting progress on persistent blockers and users finding
  Sol adequate at less perceived cost. These are uncontrolled personal reports;
  many compare earlier Sol versions, not current GPT-6.1 Sol. They justify testing
  the difficult-blocker hypothesis, not a claim of general superiority.
- [A direct report and discussion of overengineering](https://www.reddit.com/r/codex/comments/1w936rv/finding_gpt6_astra_incredible_but_wildly/)
  describes unnecessary complexity on straightforward work and suggests limiting
  architecture scope. This informs the role's minimum-change and bounded-question
  instructions. It is anecdotal, not a prevalence estimate or controlled test.

Repository bytes, compressed Git history and model input tokens are different
quantities. The packet uses selected base/head revisions, dirty-file context and
focused paths instead of assuming an entire history is cheap to ingest.
