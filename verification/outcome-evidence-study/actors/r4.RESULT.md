# Result

Implemented a bounded, offline stream receiver and quick tests/benchmark that read every current `cases.json` entry. The receiver searches every feasible start and shared integer offset from -10 to +10 Hz, without receiving the true start, offset or bits. It is given the sample rate, symbol duration and bit count. Correlation, acquisition, search and decisions are included in the timed processing; waveform generation and reusable oscillator preparation are excluded. Updated `README.md` with usage and interpretation.

Commands and observed results on this computer:

- `python3 -m unittest -v`: 3 tests passed in 0.123 s, including a subtest for each current case.
- `python3 benchmark.py --seconds 1`: 12 effective CPUs and approximately 9,648 MiB shared memory headroom. All listed messages recovered exactly. These are short sustained repeated-input measurements:

| case | recovered / expected | detected start / true | offset / true (Hz) | wall s per input s | wall real-time margin | CPU s per input s | CPU-only streams/core | prepared + processing peak MiB | allocation-only workspace count |
| --- | --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| local | 101101 / 101101 | 32 / 32 | 0 / 0 | 0.01136 | 88.0x | 0.01136 | 88.0 | 7.64 + 0.21 | 1229 |
| offset | 010110 / 010110 | 41 / 41 | +6 / +6 | 0.01115 | 89.7x | 0.01113 | 89.9 | 7.57 + 0.21 | 1240 |
| weak | 110010 / 110010 | 29 / 25 | -5 / -5 | 0.01038 | 96.3x | 0.01038 | 96.3 | 7.50 + 0.21 | 1251 |

Assuming linear scaling, the CPU-only estimates for 12 CPUs are 1056.5, 1078.5, and 1155.7 streams respectively; the traced allocations at these ceilings would consume 86.0%, 87.0%, and 92.4% of the observed shared memory headroom if every stream had separate tables. These are rough bounds, not demonstrated capacity: no concurrency scaling test was run; table sharing, samples, interpreter/allocator overhead, other workloads, quota changes and contention matter. Input duration includes leading/trailing samples. Repeated measurements reuse the same received samples, and preparation is only amortizable for matching geometry.

Additional robustness probe, exactly:

```sh
python3 - <<'PY'
from receiver import load_cases, synthesize, prepare, receive
for original in load_cases():
    success = 0
    timings_exact = 0
    offsets_exact = 0
    for seed in range(20):
        c = dict(original, seed=seed)
        samples = synthesize(c)
        tables = prepare(c['sample_rate'], len(samples))
        bits, start, offset = receive(samples, c['sample_rate'], c['symbol_samples'], len(c['bits']), tables)
        success += bits == c['bits']
        timings_exact += start == c['leading_samples']
        offsets_exact += offset == c['offset_hz']
    print(f"{original['name']}: {success}/20 exact messages, {timings_exact}/20 exact starts, {offsets_exact}/20 exact offsets")
PY
```

Output: local 20/20 messages, 17/20 starts, 20/20 offsets; offset 20/20, 13/20, 20/20; weak 19/20, 5/20, 19/20. This tiny deterministic sweep is illustrative, not an error-rate estimate. The listed weak case recovers all bits despite a four-sample timing error.

Limitations / remaining work: no unknown-length detection, fractional-Hz frequency search, clock drift, continuous streaming, real hardware, statistically reliable error rate, or measured multiworker capacity. A new or harder case may intentionally fail the recovery test; it is not silently omitted. Full receiver engineering or sustained parallel and memory measurements would be needed for those conclusions.
