# Targeted autonomous arithmetic-choice refinement

Set before d05 or the new transfer workers. This is a new wave, not a replacement
for the original results or protocol. f12/f24 remain product passes but are
numerical-objective misses: both kept wide hot products/sums without a comparison,
and the retained post-holdout discriminator found faster qualified alternatives.
The mandatory completion reviewer required this refinement before concluding.

## Prompt and development

`prompt-v3.txt` adds a general distinction between storage and executed arithmetic,
requiring a bounded credible comparison where narrower arithmetic plausibly helps.
Concrete output needs can justify local wide or exact arithmetic. No exhaustive
dtype sweep, particular witness implementation or all-FP32 answer is required.

A fresh unsteered worker runs the retired FIR starter as development regression
d05. It receives the complete candidate once, ordinary product task and public
source/checks, without previous implementations or arithmetic-specific advice.
This is regression, never new holdout evidence. Refine and refreeze again if it
does not demonstrate the intended behavior.

## New transfer envelope

After a successful development regression, freeze the candidate and assign two
fresh workers to each of three independently authored new native families:

1. Already compact storage with avoidable wider hot arithmetic.
2. A practical local wide/exact requirement, with narrow bulk work possible.
3. Shared preparation/algorithm choice and useful automatic capacity, including
   the first demanding request and supported overrides.

The same model/effort requests and bounded run allowance as the prior wave apply.
Workers get no witness, private evaluator, another answer or corrective user or
coordinator input. Generated public-check feedback and autonomous repairs are
allowed. Source/check/build files must stay in the assigned workspace. Managed
temporary directories created by supplied check programs are allowed. Build
examples must use local paths and must not contradict that scope. No Git commands,
network/cloud use, delegation or external project edits are part of the assignment.

## Frozen observable acceptance

Product gates still require useful complete outputs, quality, actual resource
limits, supported overrides and truthful capability claims as applicable. Authors
must preflight baseline/witness and an omitted-work or invalid-precision control.
Independent review must reject a product-passing but unnecessarily wide solution
that merely changes storage and never examines its retained hot arithmetic.

Behavioral review additionally checks the submitted patch and command history:

- The agent examined executed arithmetic, not just buffer types or byte counts.
- Where wider hot arithmetic was inherited and a credible narrower route could
  matter, the agent investigated a bounded alternative under matching conditions.
  A concrete correctness requirement or demonstrated absence of practical gain
  may justify retaining the wider part; speculative extra precision does not.
  Credibility comes from preflight or clear source evidence and applies even
  when storage was already compact. Matching-build demanding A/B execution with
  output checks, or a concrete counterexample to narrowing, is evidence. A
  measured near-tie with disclosed uncertainty is acceptable; output passing
  alone is not. Reformulation that removes the disputed hot work is acceptable.
- The selected default has executed demanding-case evidence under the actual
  build and limits. It preserves useful work and avoids repeated preparation or
  easy-case savings that reduce useful capacity.
- Wide/exact exceptions are local and tied to observable requirements or measured
  benefit. Stable reformulation is acceptable instead of prescribed wider types.
- No corrective messages or per-stage user tuning were required. Genuine fixture
  defects, setup repairs and scope deviations remain separate and visible.

No hard speed ratio or preference for a particular dtype is silently added to a
public product contract. End-to-end measurements include preparation and output;
matched comparisons must state flags, workload and output checks. Timing-based
hard product gates need a comfortably passing witness and serialized evaluation.
Arithmetic behavior is independently reviewed even when every output gate passes.

Report all six new transfer outcomes and retain any misses. A case used to revise
the candidate becomes development evidence. Untouched replacement coverage must
be genuinely new, and another completion review must assess whether the user goal
has been met. Existing six-family v2 product evidence remains useful but cannot
be relabeled as v3 transfer or as all-correct numerical judgment.
