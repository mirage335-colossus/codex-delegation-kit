# Action recovery: development and fresh evaluation

The user requests effective, generic correction of agent stagnation, exercised
through actual development work. This campaign follows the earlier decision-only
study; its previous stopping rule does not govern this newly requested work.

## Outcome and interventions

Success requires an agent to change an inadequate trajectory, execute a useful
authorized correction or discriminator, and validate the resulting user outcome.
Naming a mismatch or listing a future action is recorded separately from execution.
Legitimate permission/resource/correctness limits and already-satisfied outcomes
are controls: extra activity or overriding them does not count as recovery.

Two complementary changes are evaluated separately:

- Tool-capable owner/worker guidance reconstructs the next action from the original
  outcome, actual constraints and observations, then performs an available useful
  correction before accepting an inherited disposition. Reviewer execution remains
  bounded by its independent-review scope; no-execution roles only route actions.
- New-result ingress refuses contradictory declarations of success with explicit
  substantive acceptance conditions outstanding. Historical replay is unchanged.
  This deterministic guard cannot discover omitted requirements or autonomously
  perform a missing correction.

The initial baseline is the maintained dirty draft at the start of this request,
preserved under `versions/baseline`, not clean HEAD or the globally installed copy.
Candidate source and generated instructions are frozen by version before dispatch.

## Runnable cases and separation

An independent builder creates two development cases with runnable source, data,
supported local commands, realistic prior work and a consequential unmet objective.
They cover a threshold overriding user value and local progress masking a whole
application gap. Another builder, without candidate wording or development cases,
creates four fresh cases covering scheduling, recoverable prerequisites, a genuine
hard constraint, and an already-satisfied objective. That builder withholds case
solutions from the prompt designer until the candidate is frozen.

Cases have explicit user-visible acceptance, protected public tests, independent
evaluators, witnesses where needed and negative shortcut checks. An independent
reviewer verifies feasibility and criterion alignment before participants run.
Fixture setup errors and fixes are preserved. No case is selected or discarded
because its baseline result is convenient. If an invalid case is repaired after
dispatch, its previous outcomes remain invalidated evidence, not replaced wins.
Baseline public checks need not all pass: a disclosed failing check or missing
generated prerequisite can be the actual trajectory under test. Preserve those
states instead of weakening tests to manufacture a green baseline.

## Execution and comparison

Exercise the exact source backend instruction path through its ordinary `prepare`
and owned execution lifecycle, using immutable backend copies, separate private
workspaces and operation records outside those workspaces. One smoke precedes
behavioral runs. Explicit settings are Luna/high, service tier `default`, local
workspace-write, never approval, disabled worker network and no nested delegation.
The runtime must verify actual settings before inference; mismatches are holds,
not permission to substitute. The tier is drawn from retained actual backend
evidence and is freshly verified, not asserted to be today's provider default.

Each owner receives the same original task information and a 240-second runtime
deadline, including setup. The existing executor verifies owned process release.
Record actual commands, patches, checks, failures, elapsed time and usage. No
self-enforced shell-call quota is used. Limit concurrent model sessions to four
and use only tiny local standard-library fixture workloads. Production pumpModem,
cloud services and external communications are outside these exercise assignments.

Development compares baseline and candidate on both cases, initially with two
independent repetitions per condition. Revise the mechanism only in response to
a specific observed failure; preserve every version and run. A ceiling is not
evidence of comparative benefit. Anchored continuations and independent challenges
may be introduced as explicitly separate development treatments when needed;
their extra effort/information and orchestration are not hidden.

Freeze a candidate before opening fresh-case outcomes. Final evaluation initially
uses two repetitions of each condition on all four fresh cases. Additional
replications must resolve a stated uncertainty, not select a favorable seed.
Inspect failed cases and correct feasible implementation defects; an exposed
final case becomes development evidence for any subsequent tuned version and
cannot be relabeled held-out. Obtain new cases if another fresh evaluation is
needed. Continue useful development rather than stopping solely because wording
has been revised or a report can be written.

## Assessment and claims

Score separately: objective/constraint fidelity; change in next priority; executed
relevant action; independent functional outcome; preservation of original checks
and ownership; faithful final reporting. Independent graders inspect patches and
execution evidence, not just model verdicts. Hard-stop and satisfied controls
must preserve the stated boundaries. An implementation witness is a feasibility
check, not a required exact solution. No textual similarity or keyword score
substitutes for observable behavior.

Prefer materially better verified outcomes across distinct mechanisms without
control regressions. Small samples establish case-specific evidence, not universal
reliability. Report every result, including baseline successes, candidate failures,
setup limitations and reviewer corrections. Include model usage and overhead where
observed; cached tokens are part of input, not additional usage or dollar costs.

Backend behavioral tests establish that backend's exact instruction delivery;
they do not establish a native runtime interceptor. Native role/configuration
delivery requires separate existing distribution checks and, where useful,
fresh native exercises labeled with their actual instruction-loading limits.
The final source change needs independent review, appropriate regression checks,
and the mandatory Astra completion review. Follow the kit's authorized
source-to-install workflow once the change is validated; preserve user settings,
role pins, manifest inventories, historical state and publication boundaries.
