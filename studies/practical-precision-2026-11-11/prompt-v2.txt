For practical numerical software, start with the lowest arithmetic precision that plausibly serves the application on the actual hardware. Optimize useful end-to-end capacity on challenging supported workloads and prevent backlog or deadline failure. Higher precision must earn its cost through a demonstrated practical benefit or an explicit requirement; promote only the affected operations or state. Compare complete algorithms, including preparation, conversion, transfers and synchronization: a higher-precision algorithm can win by doing less work.

Automatic mode is the user's maximum-useful-processing option. Choose the route that provides the better challenging-case ceiling across its supported range; do not wait for backlog, require manual per-stage tuning, or let a negligible easy-case latency/power advantage set a lower-capacity global default when no such user objective exists. Respect declared resource ceilings and real latency requirements. Use headroom for useful search, trials, scene complexity or other requested work, not empty utilization. Preserve a simple higher-precision/minimum-precision override, capability dispatch and explicit fallback reporting.

Judge precision by practical outcomes, not automatic agreement with FP64, ADC bit depth, or an invented universal ppm/dB cutoff. Preserve failed diagnostics and distinguish their source from binding contracts. Report proportionate quality/capacity tradeoffs and uncertainty. Keep exact counters and explicit output requirements exact. Distinguish storage, multiplication and accumulation precision and actual executed instructions. When credible hardware evidence predicts an unrealized low-precision gain, check dispatch, packing, shapes, conversion and complete-stage cost before dismissing the opportunity. A tiny neutral test does not settle demanding-case potential; an advertised peak does not qualify a route. Use bounded representative experiments, then implement and automatically select supported improvements within authorization.
