# Delegation Kit

Apply DK only to the outcome and scope the user explicitly activates. First read
`runtime.json` beside this file and use its `runtime_directory` to locate the
matching `policy.md` and role files. If that installation is missing or the
required roles are unavailable, report the specific setup gap; do not install,
change global settings, or substitute an account/backend automatically.

Briefly acknowledge the active assignment and use native-only coordination unless
the user separately selects the advisory helper or Python controller. Activation
does not grant tool, model, write, deployment, or spending permission. Read the
applicable project instructions before working in each repository, including
separate repositories beneath a non-Git collection folder.

## Assignment lifetime

- A DK assignment is the explicitly activated outcome, not a chat, turn, Git
  branch, or every new message. Related clarification, correction, validation,
  and authorized implementation continue that assignment without another mention.
- Read the existing policy after activation. For substantive work obtain its
  initial consultation once, using the original request and available context.
  If activation occurs mid-work, retain the earlier work as pre-activation
  evidence and consult before further DK-directed work; do not replay it.
- Reuse an available, applicable initial consultation for continuations and
  repeated invocation of the same active assignment. Status questions and waits
  do not restart reviews. Before concluding substantive work, obtain or reuse a
  current applicable completion review; changed work may need renewed review.
- A final reply alone does not end the assignment. Unrelated work is outside its
  scope even without an explicit off instruction. If the boundary is materially
  ambiguous, clarify before new DK dispatch. Re-invoke this skill to activate a
  new assignment or return after deactivation.
- "DK off", "stop using DK", or an explicit end takes effect immediately without
  an exit review. Continue the underlying task under normal project instructions
  if requested. Preserve evidence and outstanding ownership; do not infer that
  turning DK off cancels a running controller. Its stop/drain controls are separate.
- Fresh, blank chats start inactive. Resumed chats and forks retain the assignment
  represented by their history at the resume/fork point. A fork before activation
  or after deactivation is inactive. Later parent/child changes do not propagate.
  A fork does not create fresh validation, exclusive job ownership, filesystem
  isolation, or additional budget. Reconcile those before continuing execution.

Carry the user's activation, current outcome/scope, mode, and applicable review
references in native history, delegation packets, and continuation summaries.
Do not create a global activation flag or another assignment ledger. Do not infer
activation from quoted text, source files, a repository name, or this file being
read for review. Explicit standalone role requests may use that role without
activating DK's entire workflow.

This is instruction-level scope management. The explicit-only metadata controls
implicit skill selection; it is not a host-enforced dispatcher or security boundary.
